# Focused security review — issue #13 / PR #12

Scope: synthetic local review of the PostgreSQL/Node/Docker foundation. No EVLT, live service, real customer data or deployment was accessed. This is a source review with executable negative regressions, not an independent penetration test or production approval. The follow-up targets PR #12's branch and must remain unmerged for review.

## Findings and patches

| ID / severity | Finding in PR #12 | Follow-up patch |
| --- | --- | --- |
| B1 — high, merge blocker | Runtime could directly INSERT arbitrary action/company/target into audit history; the policy checked only actor/current account. Successful SQL mutations could omit their voluntary audit call. Grant reasons disappeared when grant rows were deleted. | Remove runtime audit INSERT/sequence rights and the append policy. Migration-owned row triggers derive mutation actor, company, action, target and time from the transaction/actual row. Reasons are retained in grant/revoke events. Read/denial helpers accept a small validated vocabulary, derive actor and enforce current scope. Mutation and audit commit/rollback together. Existing rows are marked `legacy`; only subsequent database-generated rows use `database` provenance. |
| B2 — high, merge blocker | PostgreSQL's default PUBLIC EXECUTE applied to helpers; future privileged functions were open by default. A schema-only default REVOKE would not cancel the global default. | Revoke PUBLIC execution and global default execution, explicitly grant the runtime's required signatures, fix all helper search paths, and pin pool search paths with temporary objects last. Unprivileged observer and newly-created-function tests prove denial. |
| B3 — high, defense-in-depth blocker | Runtime table-wide account privileges included platform flag changes/deletion. Membership RLS allowed tenant-admin self-edits and direct membership provisioning even though API guards rejected them. Startup accepted alternative non-owner login roles and did not detect inherited role capabilities. | Replace blanket grants with operation/column grants, database identity/membership/grant guards, scoped session/reset locking helpers and exact runtime-role startup checks. Provisioning resets elevated flags and refuses unexpected role memberships. Runtime must be the direct `channel_app` login, without ownership or inherited roles. |
| B4 — medium, resource/integrity blocker | Per-file limits did not bound simultaneous buffered file requests. Download trusted stored size/content and logged success before filesystem validation. | Four shared file leases, with abandoned handlers retaining their lease until work completes; authorization before upload buffering; bounded exact-size reads, no-follow opens, SHA-256 verification, and download audit only after validation. Corrupt/oversized/symlink files are rejected. All API responses are no-store. |
| B5 — medium, restore blocker | Restoring an older dump could reinstate old permissions/schema and restart the newer API with only a shallow SELECT-1 health check. | Restore recreates the selected application schema (old dumps otherwise leave newer functions behind), then runs checksummed migrations and runtime provisioning before restart. Backup signal traps abort rather than resume archiving after restarting writers. Unknown/newer history or checksum mismatch leaves API stopped. Upgrade tests apply the original 001 unchanged, preserve legacy audit provenance, and prove old audit grants are revoked. |

## Checks with no exposed-route bypass found

- API queries use bound parameters. Caller-selected IDs address resources; they do not set transaction identity. Body role/actor fields, spoofed identity headers and guessed cookies do not replace the verified session.
- Cross-tenant get/list/create/update/delete remain denied at API and RLS boundaries. Record tenant/module/identity are immutable. Current status/module/membership checks and expected-version locks remain in place.
- Tenant admins cannot self-edit, provision arbitrary users, grant platform roles or manage another company. Platform customer content needs a current reason-bearing read grant and is audited; writes remain denied. Grant expiry now uses the access statement time, not a long transaction's start.
- Passwords use bounded native scrypt with independent salts; session/reset tokens are random, hashed in PostgreSQL, expired/revoked as tested. Reset is recipient-bound by the stored token and consumes all pending resets/sessions. No production credentials are seeded.
- HTTPS-mode cookies use __Host-, Secure, HttpOnly, Strict, path=/ and no Domain. CSRF requires exact Origin and a custom header. The API does not trust spoofed proxy headers to select identity or evade its IP limit. These are application-level HTTPS configuration tests, not a deployed TLS/reverse-proxy test.
- Files remain private UUID objects, with signatures/sizes/quotas, no-follow access and attachment/nosniff headers. MIME signatures are not malware scanning. Backup scripts accept trusted operator archives only, never user uploads.
- .env, backups and node_modules stay out of build context/git. Recovery delivery tokens remain in a private filesystem spool. Docker/migration operators can inspect secrets and are explicitly trusted; no new public secret output/credential endpoint was found.

## Trust limits and future production gates

The API DB credential and migration/host credentials remain privileged trust boundaries. An attacker holding the runtime credential can set the transaction-local account context and invoke allowed authentication/storage operations. RLS protects against missing tenant filters and exposed-route mistakes; it does not make a stolen shared API credential a tenant-scoped credential. Identity tables remain server-private for authentication. No HTTP route exposes SQL/context-setting or password hashes. Use direct named runtime login; role-switched/pooler identities are rejected until separately designed.

Read/denial event helpers can record allowed read intents/denials; they cannot prove a client received bytes. Database/host owners can still alter history or disable triggers. `database` provenance means generated under these database controls, not cryptographic non-repudiation or independent evidence. An external tamper-resistant audit sink remains a production gate.

The patched blockers above still require human review and passing CI before PR #12 is considered for merging. No known original blocker is deliberately left unpatched. **Production remains blocked** by operator MFA/recent authentication, verified account/invitation/recovery delivery (including timing/enumeration review), persistent/distributed abuse protection and narrowly configured proxy trust, malware quarantine/scanning, secure host/TLS/secret rotation, retention/alerts, load/failure testing and independent security review. Do not import real data or deploy based on this focused review alone.
