# Stage 5: administration workflow delivery

The reporting, notification and communications implementation in STAGE5-DELIVERY.md is retained. This continuation implements the remaining core Stage 5 browser-demonstration workflows, rather than replacing earlier modules. PAGE-CHECKLIST.md records outstanding advanced features and earlier-stage/owner-console gaps; the complete original application specification is not finished.

## Working pages and integrations

- **Approvals:** pending, assigned, urgent, approved/rejected and changes-requested queues. An existing active staff profile makes decisions, with reasons, assigned approver, self-review checks and decision history. Stale/repeated decisions are rejected. Supported records include leave, completed timesheets and correction requests, task approvals, submitted inspections, maintenance completion, documents and quotations awaiting approval. The original record updates immediately. Approved leave affects assignment availability; approved corrections change hours only after approval. Request changes and resubmission preserve history. Existing module-specific approval controls remain available; this is not a production approval authorization system.
- **Roles and access:** six templates, editable custom roles, module/action/team controls, optional ownership/location scopes and sensitive-record visibility. Demo mutation wrappers check the current role, company, module and record. Staff and volunteers start with their own work. Staff-profile editing requires Manage staff. Settings/automations require Manage; reports require Reports. Administration access cannot accidentally remove its own View/Manage actions. Fictional role/actor switching is explicitly browser-only and provides no secure authentication.
- **Automations:** name, supported trigger/action, optional priority condition and enabled state; explicit evaluation and execution/error history with source/target links. Inspection failure creates corrective maintenance; maintenance completion creates a follow-up inspection; completion creates the next recurring task. Source IDs and existing linked targets prevent duplicates, including manual corrective jobs or existing recurring successors. Processing is non-recursive. New task assignments are retained only when eligibility is valid. Unsupported target modules produce visible errors. There are no background jobs when the browser is closed.
- **Company settings:** company profile and industry, contact/address, departments/locations, working days/hours, leave allowance, minimum shift coverage, modules/dependencies, custom roles/scopes, local logo, accent, welcome text, navigation labels, notification defaults and central self-review policy. Settings are isolated to the selected fictional company and update the workspace immediately. Industry changes preserve existing records and modules. Reset-to-template applies the industry's dashboard preset. Local image data stays in browser session memory.
- **Dashboard:** additional maintenance, inventory, qualifications, events, bookings, visitor, financial and approval widgets, filtered by permitted enabled modules. Widgets retain current-record values, removal/reordering/width controls and per-widget record limits. Administrators save the company session layout; other users can adjust their local view. Reset restores the industry template.
- **Global search:** header entry point and responsive command palette with keyboard focus, Escape and grouped permitted records. Stable IDs open the associated profile. Commands open real task, maintenance, CRM, rota, inspection and booking workflows. Existing saved searches are retained.
- **Activity history:** record creation, meaningful field/status/assignment changes, approvals, stock and qualification changes, plus company configuration changes. Entries include fictional actor, UTC time, action, details and original-record links; filters cover date, user, module and action. Record histories are bounded to 100 entries and company configuration to 300; automation execution history is bounded to 200. These are temporary logs, not tamper-proof audit evidence.

## Architecture

Business decisions and automation processing live in `administrationRules.js`; assignment validation is separated into `demoAssignmentRules.js` and uses the existing shared eligibility evaluator against the full company dataset, including hidden leave/qualification modules. The fictional adapter publishes generated records and execution history together. CustomerWorkspace applies role and record scopes, while settings and administration pages load on demand. Configuration is stored under the existing organisation workspaceConfig, preserving the adapter contracts and backend foundation. No dependencies, external services or infrastructure were added.

## Verification

New behavioral tests cover stale/self approval, availability changes, correction timing, atomic deduplicated automation, assignment validation when source modules are hidden, recurring successor reuse, scoped records and structured activity/reset. New Playwright scenarios cover the central leave decision/engineer selector, failed-inspection automation, company configuration and isolation, widgets/search/activity, timesheet correction and forbidden viewer mutations on desktop, iPhone and iPad. Local verification: npm ci, lint, build and 95 unit tests pass; all 159 browser regressions passed before the final task-resubmission guard, with affected administration/workspace scenarios rerun after it. All 18 backend integration tests pass. CI reruns the complete browser suite on the final commit. The optional Compose smoke script was not executed beyond its disposable-instance safety guard; no running Compose environment was altered. Final CI and deployment evidence are recorded in the pull request.

## Boundaries

All data and payments remain fictional; refresh or Reset Demo clears changes. No real notifications, emails, push messages, billing, permanent file uploads or closed-browser automation are claimed. Reports retain the native Excel, overtime/project and scheduling limitations described in STAGE5-DELIVERY.md. Advanced resource calendars, document handling, Fleet/Inventory/CRM extensions and owner-console work remain on PAGE-CHECKLIST.md. Server authorization, persistence and production deployment are separate from this public demo. EVLT is untouched and GitHub Pages remains the only public hosting target.
