# Channel Systems tenancy decision — issue #4

Status: **recommendation for review, not authorization to provision or migrate**. Reviewed 6 November 2026 using the public vendor sources below, the updated [Firebase design](FIREBASE-DESIGN.md) and [backend contracts](BACKEND-CONTRACT.md). No EVLT repository, Firebase project, credentials, accounts or data were inspected. Its current edition, region, plan, quotas, Rules, IAM and usage remain unknown.

## Recommendation

Keep EVLT independent. Prefer a **new, separate Channel Systems / Owner Admin Firebase project** when quota approval and the required operational budget are available. It can host Channel Systems' future tenants with explicit server authorization; separate-project placement alone does not isolate those tenants from one another. Do not reuse EVLT as a shortcut around project limits. Under the present no-billing/no-live-access constraints, continue the fictional demo and offline policy work.

EVLT reuse is **too risky to approve on current evidence**, rather than technically impossible in every future design. It couples an unassessed live system to new identity, authorization and operational changes. A scoped Firestore path does not remove that coupling. There is no evidence here that EVLT is insecure; there is insufficient evidence to safely change its trust boundary. A separate project reduces accidental cross-product impact without requiring any EVLT migration.

If separate Firebase approval remains blocked, evaluate a separate managed Postgres/Supabase project as the next candidate. A free tier is suitable for a synthetic evaluation, not evidence that production recovery, availability, MFA and support needs can be met at zero cost. Self-hosted Postgres plus an API and OIDC provider is an alternative only if somebody owns patching, recovery and incidents; a small VM price is not the total operating cost. None of these alternatives is provisioned here.

## Why `organisationId` is insufficient

An organisation ID is an address supplied by a caller. In a shared project, registering another Firebase app does not create a second Auth or administrative boundary [S1]. Filtering `/organisations/{id}` in JavaScript cannot protect any data already downloaded. Firestore queries must be authorized at the data boundary; Rules evaluate whether a query could return forbidden results rather than filtering them away [S4].

Identity Platform tenant IDs and application organisation IDs serve different purposes. If distinct identity silos are selected, map a verified **issuer/project + identity tenant + UID** to authorised application memberships. Never trust a tenant selector, URL, claimed role or body UID as that mapping. Reject a valid token from the wrong project/identity tenant. Recheck current account, organisation, membership and module state; old claims cannot restore revoked access.

Identity silos do not automatically scope privileged database services, backup jobs, exports, logs or storage. Each trusted handler still needs explicit tenant checks, and each service identity needs least privilege. A compromised privileged path can bypass an otherwise correct client policy [S4]. Separate projects reduce this risk only if credentials and IAM are actually separated.

### Identity Platform requirements and cost: sourced versus unknown

Public documentation confirms user/provider silos [S2], a billing-enabled project and setup permissions for multi-tenancy [S3], and an Identity Platform upgrade for Firebase TOTP MFA [S8]. The pricing page describes MAU/provider-based charges and phone/MFA messaging charges [S13]. None of those capabilities was enabled or tested here.

Actual eligibility, feature compatibility, identity-tenant quota, provider-specific MFA behavior, migration compatibility and the bill for this workload remain **unverified**. No assumption of free identity tenancy, free SMS or a per-tenant allowance is approved. Before any live decision, obtain a dated estimate using expected MAU, provider types, MFA method/message destinations, database operations/storage, egress, API hosting, backup/restore and support requirements. Do not extrapolate a general pricing page into an EVLT quote.

## Contract review and implications

The existing `Backend` is a fictional UI boundary: `getSession()` returns null and its snapshot includes all sample organisations. It must not be connected to a live database as-is. The organisation directory needs a platform-authorized projection; tenant record/ticket APIs need tenant-scoped queries. Membership and entitlement `replace` commands need validated server roles, versions and audit; browser audit append must become server-internal. Demo reset/settings must not become live administrative endpoints. See [BACKEND-CONTRACT.md](BACKEND-CONTRACT.md).

The offline policy deliberately uses a separate directory and is not imported into `src/`. It explores the record-port boundary only: account + organisation + current membership + allowed action + module entitlement + immutable record path + field validation. It does not retrofit “security” onto public demo filtering or claim to implement the future adapter.

## Rollout and rollback gates — future approvals required

1. **Decision gate, no live access:** review this recommendation, define identity-silo requirements, data categories, residency, RPO/RTO, support ownership and workload estimate. Resolve separate-project quota or choose another independently provisioned solution. This PR does not approve either provisioning or billing.
2. **Offline gate:** run the synthetic policy suite; approve a real API threat model. Before implementing Firebase writes, author negative emulator Rules tests and trusted-handler tests for records, memberships, entitlements, tickets, audit and exports. Include stale tokens, pagination/listeners, forged identity, module revocation and concurrent changes. Passing the current model alone cannot pass this gate.
3. **Separate synthetic staging gate:** only after explicit project/resource approval, provision a separate Owner Admin environment. Verify Auth token issuer/tenant/MFA, Rules, IAM, indexes, logs, rate limits, transactions, backups and region. Rehearse export/deletion/restore with synthetic tenants. No EVLT access is necessary for this recommended path.
4. **Launch gate:** independent security/privacy review, cost/alert plan, least-privilege credentials, named incident owner, tested recovery, explicit real-account/data authorization and approved production deployment. Keep the public fictional demo separate.
5. **Rollback gate:** before launch, record the prior app/API/policy versions, compatible schema version, write-stop procedure, recovery point and owner. On authorization leakage, failed revocation, unexplained cross-tenant data, incompatible migration or restore failure, stop affected writes/access and preserve restricted evidence. Roll back to a compatible policy that retains tenant protections; never restore a permissive rule just to restore availability. Reconcile writes before restoring data; reverting code does not undo data mutations. No rollback may target EVLT under this issue.

If shared EVLT is reconsidered, require a **separate explicit authorization** before any inspection of its live setup. A future independent review would need evidence about its Auth migration, privileged services/IAM, all data paths and clients, region, capacity, recovery and an EVLT-specific rollback rehearsal. Unknowns are blockers, not permission to inspect. Until then, do not enable Identity Platform, add tenants, change Rules, rotate credentials or run a migration there.

## Precisely what is verified

The reproducible [offline policy proof of concept](../proof-of-concepts/tenant-authorization/README.md) has **14 named test cases** (with action/tenant variants) for synthetic A/B access, cross-tenant reads/writes/lists, forged IDs/roles, revoked/missing membership, disabled modules, unauthenticated/suspended principals, role limits, default deny and schema/identity invariants. `npm test` includes them automatically; `npm run test:policy` runs only those tests without dependencies or network access.

Local verification on 2026-11-06 passed: `npm run test:policy` (**14 policy tests**), `npm run lint`, `npm test` (**30 total unit/model/policy tests**), `npm run build`, and `npm run test:e2e` (**30 Chromium browser tests**, desktop/phone/tablet). The policy command also passed from a standalone temporary copy containing only the policy, synthetic fixtures, test and a module-type package manifest, with no `node_modules` or Firebase configuration. The browser suite protects the existing fictional demo and is not a tenant security test. The existing CI `npm test` glob includes the new policy tests without any workflow changes; see the PR check for its execution result.

**Not verified:** Firebase Rules/emulators, SDK integration, token cryptography/issuers/identity tenancy, live revocation latency, Admin SDK/IAM, distributed transaction/race behavior, real backups/restores, production costs/quotas/regions, provider MFA or any property of EVLT. No live integration, credential, account, deployment or paid service was created.
