# Backend boundary and fictional adapter

## Current implementation

`src/main.jsx` only mounts the app. `App.jsx` composes the shell, customer workspace and owner pages. `pages/` contains one component per owner workflow; `layout/` holds navigation, dialogs and backend states. `useConsoleController` owns UI selection and actions; `useDrawer` owns focus and keyboard handling; `useBackend` owns loading, retry, errors and subscription cleanup.

`src/backend/contracts.js` specifies the asynchronous ports and validates adapter shape. `src/backend/fictional.js` is the **only adapter**. It uses fresh fictional fixtures in memory, never network calls, browser storage, credentials, account creation or Firebase. Reloading the page or clicking **Reset fictional demo** restores fixtures. Tabs have independent state. Reset also restores navigation, flags, prices, tickets, record progress and local activity. Nothing is sent to customers. Never enter actual personal or customer information.

The adapter publishes a stable, deeply frozen snapshot for `useSyncExternalStore`; list/load results are detached copies. Mutation methods return Promises and publish after a successful local change. A failed mutation rejects, preserves the prior snapshot and shows a UI alert. `load` failures have a retry action; loading and empty organisations hide tenant-dependent pages. Empty support selection has its own state. These behaviors are tested through injected adapters, with no shipped fault flags.

## Ports

| Port | Operations | Fictional representation / future requirement |
| --- | --- | --- |
| Authentication | `getSession()` | Always `null`; no simulated login or real user. Future verified session includes UID, authentication time and MFA assurance. |
| Organisations | `list()`, `create(values)`, `update(orgId, patch)` | Profile, sector, branding, status and illustrative plan. Create seeds records in one local publication. Future platform-only directory, scoped tenant profile and server-owned lifecycle. |
| Memberships | `list(orgId)`, `replace(orgId, members)` | Names and role labels in `org.admins`, not accounts. Future UID-keyed membership records with status, version and granular permissions. No real invitations here. |
| Module entitlements | `list(orgId)`, `replace(orgId, modules)` | `org.modules`; dependencies are handled by the model/UI. Future server validates the full dependency graph and owns grants. |
| Records | `list(orgId)`, `create(orgId, values)`, `update(orgId, recordId, patch)` | ID, orgId, module, title, detail, progress. Scoped writes reject unknown/mismatched addresses and identity changes. |
| Support tickets | `list(orgId)`, `create(orgId, values)`, `update(orgId, ticketId, patch)` | Fictional subject, priority, status and local history; scope/identity cannot be changed by update. Future explicit support assignment with limited access. |
| Audit events | `list(orgId)`, `append(orgId, event)` | Bounded 200-event local activity list with browser time. Future events must be generated by trusted server operations, with append unavailable to untrusted clients. |
| Demo settings | `setPlans(updater)`, `setFlags(flags)` | Local examples only. Not an authorization or billing API. |

All tenant-addressed calls require an org ID even when the UI already selects an organisation. That ID is an address, **not authority**. Every production operation must independently authorize the actor, target organisation, resource, module and action.

The local snapshot intentionally contains all fictional organisations, including retained records for disabled modules. Client filtering and demo ID checks are correctness aids, **never tenant isolation**. Suspended organisations remain previewable for demonstrating UI. Local membership labels, feature flags and module controls confer no production rights.

## Future remote adapter requirements — not implemented

Do not plug a database directly into this all-fixtures projection. A remote adapter must build separate owner and tenant-authorized projections from server-authorized queries, clear cached data on logout/revocation/tenant switch, and never fetch an unrestricted tenant collection then filter in the browser. The owner directory requires a separately authorized platform operation. Empty/loading UI must not briefly reveal an old tenant snapshot.

The Promise/port boundary supports an eventual remote implementation, but demo bulk membership/entitlement replacement must become validated, versioned server commands; demo settings and reset must never become unrestricted production endpoints. Audit append must be internal to the trusted service, not a browser request that accepts arbitrary actor/time/outcome. No Firebase adapter exists in this PR.

Define stable error codes before implementing remote calls: unauthenticated, forbidden, unavailable/not-found (avoid existence leaks), invalid input, conflict, rate limited and transient failure. The current UI deliberately shows generic fictional-demo errors. Never expose server stack traces, tokens or personal data in errors. Define request limits, schemas, pagination, cancellation and retry/idempotency for remote writes before live use.

In-process changes are sequenced synchronously before their Promise resolves; simultaneous demo creates preserve independent changes. `getRevision()` is only a local notification counter, not a distributed version check. Production updates need per-resource expected versions and Firestore transactions; stale edits must return conflict, not silently overwrite another user's change. Provisioning and invitations require idempotency keys. Privileged mutation plus audit outbox must commit atomically; retrying an operation must not duplicate its effects.

See [future Firebase design](FIREBASE-DESIGN.md) and [threat model and security test plan](THREAT-MODEL.md). Passing demo tests establishes UI and adapter correctness only.

## Offline service implementation (issue #6)

A separate [offline backend foundation](OFFLINE-BACKEND.md) now implements protected-style resource ports with fake sessions, memberships, invitations, configuration, versioned CRUD and internal audit. The public adapter described above remains unchanged. The offline service deliberately excludes unsafe demo snapshot/reset/bulk replacement/audit append ports; it must not be mistaken for live authentication or database isolation. See the linked port reference and future integration checklist.

## Firebase preparation interface (issue #8)

[Firebase preparation](FIREBASE-PREPARATION.md) provides configurable, offline-only auth and record ports using an injected synthetic transport. It preserves the offline service's signatures while intentionally excluding unrestricted demo ports. No Firebase SDK or live connection exists; prototype Firestore Rules deny all direct client access.
